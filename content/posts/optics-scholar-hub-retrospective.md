# 从资料汇总到可维护的科研工具：光研导航开发复盘

> 由 Codex 整理，ZhaoYan 提出需求并参与项目迭代。本文依据项目源码、数据、验收记录和原始复盘稿重写，整理日期：2026-10-10。本文是协作开发记录，不代写作者的个人感受；历史测试结果引用当时的记录，不代表本次重新执行了全部测试。

查找一本适合的期刊、确认一场会议是否还能投稿，通常需要在期刊官网、作者指南、分区平台和会议通知之间反复切换。光研导航试图把这些分散入口组织起来，让光学研究生能够先筛选，再回到原始来源确认。

项目从期刊与会议目录逐步发展为包含组合筛选、期刊对比、会议系列、日历导出和来源巡检的静态网站。开发过程中的主要难点也随之变化：页面能否运行只是起点，信息如何表达、变化如何维护、一个版本如何结束，才决定它是否适合长期使用。

[在线使用光研导航](https://uestczhaoyan-gif.github.io/optics-scholar-hub/) · [GitHub 仓库](https://github.com/uestczhaoyan-gif/optics-scholar-hub)

## 1. 从使用需求确定项目边界

光研导航借鉴了 CCF-Deadlines 集中呈现会议安排的思路，但没有沿用计算机领域的会议等级评价。光学研究横跨材料、电子、物理、生物医学和计算等方向，期刊范围、会议形式与投稿要求都需要按实际来源整理。

因此，网站首先服务于一个具体过程：按方向找到候选期刊或会议，查看适用的索引、分区和时间信息，比较投稿准备要求，最后打开官网确认。它提供查找和核对的入口，不承担毕业认定或投稿录用判断。

这一定位影响了后续取舍。缺失信息需要明确显示，来源和核验日期需要保留；即使页面能够给出一个看似完整的答案，也不能填入通知中没有公布的时间或未经核实的分区。

## 2. 架构选择：先让公开目录易于更新

网站采用 React、TypeScript 与 vinext 静态导出，数据保存在 JSON 文件中，通过 GitHub Actions 检查并发布到 GitHub Pages。访问者的搜索与筛选在浏览器中完成，不需要站内账号、数据库或运行时 AI 服务。

| 组成 | 作用 |
| --- | --- |
| `data/` | 保存期刊、会议届次、稳定系列、活动及候选记录 |
| `app/`、`components/` | 组织页面、卡片、筛选和对比界面 |
| `lib/` | 处理日期、检索、分区、分享与日历等规则 |
| `scripts/`、`tests/` | 执行数据校验、来源巡检、维护报告与规则测试 |
| `docs/` | 保存设计依据、事实证据、验收与维护记录 |

对这个以公开资料查阅为主的项目，静态架构减少了服务端维护负担。JSON 与 Git 配合，也能清楚显示某个字段为什么发生变化。代价是更新需要经过构建发布；本地关注依赖当前浏览器，日历导出只是当时的快照，不提供账号同步或持续订阅。

```text
官方资料与核验记录
        ↓ 审核后修改
JSON 数据 + 页面与规则代码
        ↓ 校验、测试、构建
GitHub Actions → GitHub Pages
        ↓
浏览器中的检索、筛选、对比与导出
```

这条流程将资料核验与页面发布分开：今天重新构建网站，不等于所有期刊和会议都在今天重新核实过。

## 3. 数据模型中最重要的几个区别

### 分区、索引和来源不能混写

“一区期刊”不是足够完整的描述。项目分别保存 JCR 与中科院分区，记录版本、学科和来源；JCR 还区分版本年与指标年，中科院区分大类与小类。一条学科记录不能自动代表其他学科，旧版本也不能无说明地当作今年的结果。

SCI/SCIE、ESCI、EI 与分区另设字段。出版社声明、数据库方来源表和具体查询证据分别记录，尽量通过 ISSN 等标识核对期刊身份。期刊出现在来源表里，并不意味着某篇论文已经被检索。

这些区分会增加数据与界面的复杂度，却让访问者能够判断一条信息究竟支持什么结论。对没有足够依据的字段，保留未知比补出一个确定答案更可靠。

### 只有日期，就不制造精确倒计时

会议通知可能公布完整时间与时区，也可能只有某一天。项目将精确时间、仅日期和未知分开处理：只有来源明确时才转换时区，不把日期级信息自行补成当天 23:59。

事件类型同样影响判断。投稿、PDP、录用确认、注册和终稿各有含义，未来还有一个事件不代表现在仍可提交新论文。后续体验改进中，IEEE MEMS 2027 的作者接受确认事项就被纠正为确认事件，保留原日期与来源，同时避免误导投稿状态。

### 系列与届次分别维护

一个会议系列可以持续多年，但每届的日期、地点和要求需要独立保存。项目为此增加稳定系列与往届入口，使访问者能够沿系列查历史、关注未来公告。

尚未公告的下一届不会按往年规律推算；展览、论坛也与论文会议分开。先把对象分清，才能避免用统一模板生成实际上不存在的投稿截止。

## 4. 从持续扩充转向有限验收

目录很容易无限延伸：新增一批期刊之后仍有更多候选，核完一届会议之后又会出现下一届。若“继续完善”一直是唯一目标，项目就难以进入可交接的维护阶段。

2026-10-05 的结项规划固定了 V1.0 范围与验收门槛，将功能、正式条目、候选审核、交叉期刊样例、核心系列和发布交接分开验收。新增发现不再自动扩充本轮必须完成的任务。

根据 [V1.0 验收记录](https://github.com/uestczhaoyan-gif/optics-scholar-hub/blob/main/docs/V1_ACCEPTANCE_2026-10-06.md)，项目于 10 月 6 日完成这一轮建设：固定的 60 项候选均完成审查，8 项准入，其余 52 项保留具体限制及后续触发条件；当时的目录包含 112 本期刊，记录了 32 项测试通过以及界面和部署核验结果。

这里的“审查完成”与“全部信息已知”不同。来源受限、缺少当届通知或证据不足，都可以成为有记录的审查结论。版本完成意味着约定范围已经处理并交接，不意味着目录覆盖了整个领域。

## 5. 上线之后，再按真实任务检查

V1.0 验收后，项目又进行了一轮使用体验改进。功能是否存在与访问者能否顺利完成任务，需要分开检查：目录中有数据，用户仍可能搜不到；有筛选选项，手机上仍可能难以操作。

| 使用中的问题 | 本轮改进 |
| --- | --- |
| 长列表难浏览 | 增加分页、名称排序与中文别名检索 |
| 手机筛选占据太多空间 | 筛选可折叠，已选条件可逐项清除 |
| 当前会议与历史届次混在一起 | 增加快捷筛选与分页，保留往届查询 |
| 多本期刊来回切换不便 | 支持跨页选择最多三本期刊对比 |
| 发现错误后不知如何反馈 | 卡片提供预填条目信息的 GitHub 纠错入口 |

这轮也补入 Nature、Science 母刊，并扩大分区筛选的可用范围。新增目录记录与改进浏览方式分别处理，避免把“数据已有但不好找”误判成“需要重新收录”。

实现这些功能时，关键约束落在具体行为上：搜索要覆盖全部目录；筛选变化后页码需重置；对比选择要跨页保留；日历导出要覆盖完整筛选结果。这些约束比单纯检查“分页按钮是否出现”更接近用户实际需要。

按本次读取的本地数据，2026-10-10 的目录快照为 **114 本期刊、133 届会议、98 个系列、10 项展会与论坛**。[体验改进记录](https://github.com/uestczhaoyan-gif/optics-scholar-hub/blob/main/docs/UX_CHECKLIST_2026-10-09.md)记载了六项改进发布及最终 41 项测试通过。它与前一节的 V1.0 验收属于不同阶段，数量差异来自后续更新。

## 6. 哪些问题值得保留为回归场景

### 搜索要接近访问者的输入

V1.0 回归时，“CLEO 2027”曾漏掉真正的当届会议，原因是检索字段未包含年份。修复时补入年份字段与回归测试。这个例子说明，数据存在并不能保证搜索入口有效，验证输入需要包含访问者会使用的系列名与年份组合。

### 响应式样式仍需实际检查

移动端曾出现导航撑宽页面的问题，三刊对比又带来了表格撑宽网格的问题。后者通过约束结果列宽度、让对比区域独立横向滚动解决。检查整页是否溢出，比仅看代码中有没有媒体查询更直接。

### 区分产品故障与工具限制

一次日历导出检查中，自动化工具等待下载事件超时，但文件实际上已经生成；随后读取文件内容，才确认导出结果。这类问题不能仅凭工具报错认定功能失败，也不能在命令返回成功后省略产物检查。

上述问题与验证范围记录在[界面回归文档](https://github.com/uestczhaoyan-gif/optics-scholar-hub/blob/main/docs/UI_REGRESSION.md)中。它们是特定环境下的核验结果，不代表所有浏览器与设备都已覆盖。

## 7. 发布与巡检怎样衔接

项目的发布工作流先安装锁定依赖，再运行数据校验、测试、类型检查和 lint，生成维护报告，最后构建并部署。由于网站位于 `/optics-scholar-hub/` 子路径，构建还需要正确设置资源路径；本地根路径能打开，不能代替子路径部署验证。

```sh
pnpm validate:data
pnpm test
pnpm typecheck
pnpm lint
pnpm build
```

这些是项目的核心验证命令。正式发布还需查看对应提交的部署结果，并检查实际网页；目录摘要能够辅助核对数据版本，但不能单独证明交互代码已经更新。

来源巡检采用另一条流程。仓库配置了每日定时检查，比较网页内容及显式图片、PDF 来源的指纹，把变化作为人工复核线索。页脚变化、文件元数据改变和限流都可能触发信号，因此巡检不会自动把变化转换为新的投稿日期。

日常维护由此形成循环：发现来源变化，阅读适用的官方通知，更新相应字段与证据，再验证、发布。浏览器检查到新的目录版本，也只说明有新的已发布数据，不代表官网刚刚被重新核验。

## 8. 对后续 AI 协作的启示

从这些记录中可以归纳出几条可复用的方法。

首先，需求应落到可检查的任务上。相比“把网站完善好”，“筛选一个方向、比较三本期刊、打开作者指南”更容易指导实现和验收。AI 能持续执行具体工作，但不能替代使用者确定目标。

其次，数据结构应允许不知道。明确的未知值、来源、版本与核验范围，使 AI 能在证据不足时停下来；否则，追求表格完整反而容易掩盖信息缺口。

再次，每轮建设需要有限范围。把候选审核、功能修复与未来维护分开，才能在当前目标达成后结束，而不是把不断发现的新任务都视为未完成。

最后，续接依据应保存在仓库。代码说明实现，证据说明事实，回归记录说明检查过的行为，验收记录说明某个版本的完成范围。下一次更新时，才能据此判断需要改哪里、复查什么，以及哪些限制仍然存在。

光研导航目前仍是持续维护的精选目录。部分来源与字段存在限制，本地关注没有跨设备同步，日历也不是持续订阅。这些边界应与功能一起呈现。后续迭代可以围绕真实反馈继续展开，而不必为了追求功能数量重新扩大已经完成的版本范围。
